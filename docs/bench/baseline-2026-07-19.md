# 基线报告：会话记忆系统评测（2026-07-19）

评测对象：VESTI 会话记忆系统（capture-core：SQLite + FTS5 + SessionRecall(FTS5+RRF) + digest 管线）。
评测基建：`scripts/bench/`（新建，独立目录，不改业务代码）；机器报告原文在 `docs/bench/out/`。
运行方式：`ELECTRON_RUN_AS_NODE=1 node_modules/electron/dist/electron.exe scripts/bench/{corpus,bench-a,bench-c}.mjs`（详见 `docs/bench/README.md`）。

## 方法与参数

**Bench A（召回准确率，RULER 式纯本地判分）**：合成库 60 会话（4 平台×15、8 项目、1794 条消息、含工具调用与闲聊/near-miss 噪声），埋 12 根单针（8 类模板：config_value/file_state/decision/owner/version/deadline/api_endpoint/env_var；其中 3 根为 CJK 连写变体）、4 组知识更新对（同键改两次，旧会话 30–45 天前、新会话 2–8 天前）、4 条多键查询、5 条拒答查询（3 条带跨 scope 诱饵）。查询集直接跑 `recallSessions`（topK=5，无向量——与线上一致，真实库 embedding 全部 skipped）。seed=42，可复现。

**Bench C（digest 保真度，程序判分）**：真实库只读快照（SQLite backup API，106 会话 / 17719+ 消息 / 106 digest），规则抽取关键事实 2438 条（决策句 653 / 文件路径 1219 / 数值 566），核对 digest 五字段覆盖率；每条事实标注是否在 digest 输入窗口内（复刻 `buildDigestTranscript`：最近 ≤60 条、尾部 6000 字符、不含 thinking）。

## 发现的系统短板

1. **中文连写事实会整段从 FTS 消失（最严重）**。FTS5 unicode61 把整段 CJK 连写视作一个 token：针原文「关于前端状态管理库，团队最终决定用Zustand了」中明明逐字包含「前端状态管理库」，查询「前端状态管理库 最终选了什么方案？」却零命中——token 不重叠，不是排名靠后而是**根本没有召回**。连写针 Recall 33.3% vs 分写针 100%；「支付模块负责人」更新对的两个会话双双零命中（证据：`bench-a-2026-07-19.md` 未命中表与时序明细）。真实库 81/106 是中文为主的 kimi-code 会话，该缺陷在生产数据上必然高频触发。

2. **召回无时序概念，知识更新后旧值压过新值**。4 组更新对里 2 组 top1 是旧值会话（「生产环境 API 服务刚发布了 v2.4.1」压过 v2.5.0；「M3 里程碑的截止日期定为 2026-08-15」压过 2026-08-29），1 组双双失踪，仅 1 组（拉丁键 timeout）新值胜出。RRF 只融合词法排名，不含任何时间衰减；BM25 对短句/旧会话无惩罚。

3. **无拒答机制，诱饵事实被当作答案呈上**。3/5 拒答查询返回了结果（其中 2 条返回满 5 条）且 top1 snippet 直接引用诱饵：问「生产环境 redis 的 maxmemory」呈上「本地开发用的 redis 的 maxmemory 是 256mb」；问 PostgreSQL max_connections 呈上「本地 docker 里…默认 100」。且这些误导命中的 RRF 分数（0.0164）与 12 条正常单针命中里 9 条的分数完全相同——**分数层面无法区分真假命中**，下游 LLM 拿到 snippet 极易照抄。OR 式 FTS 查询 + 中文功能词「的」几乎保证任何查询都有结果返回。

4. **digest 对数值类事实近乎失明**。真实库数值事实覆盖率仅 6.4%，即使在 digest 看得见的窗口内也只有 5.3%（对比决策句窗口内 41.5%）。配置值、版本号、截止日期这类「精确值」事实不进 digest——digest 只能回答主题级问题，回答不了值级问题（与 Bench A 的 config_value/version/deadline 针型互为印证）。

5. **digest 输入窗口造成结构性盲区**。48% 的事实（1174/2438）落在窗口外：窗口只看最近 ≤60 条消息、尾部 6000 字符；超长消息一条即吃光预算——真实库最大单条消息 59246 字符，最差案例 44 条消息的会话窗口只装进 1 条（`bench-c` worstSessions：`--agent-1`，windowMessages=1）。窗口外事实被覆盖纯属 one_liner 碰巧重述任务（23.6%），不是管线功劳。

6. **退化 digest 静默存在且把用户 prompt 当摘要**。7/106 digest 四字段全空（LLM 失败回退），one_liner 是首条用户消息原文截断——worst 表第一名（57 消息、21 事实、覆盖率 0%）的 one_liner 就是用户整段任务 prompt（「你是资深实现工程师。在 C:/Users/22150/…」）。这类会话结构化事实覆盖≈0，且无任何标记区分。另有 2 个 digest 滞后于会话增长（digest message_count < 当前）。

7. **snippet 呈上不携带 scope 限定**。拒答明细可见 snippet 只截取命中词上下文 ±80 字符，诱饵句的 scope 限定语（「本地开发用的」「只是本地玩玩」）恰在窗口外或被截断，用户/下游看到的是裸值「256mb」。snippet 质量本身不差（ Bench A 正常命中 snippet 均指向针句），但对「近似命中」没有视觉区分。

## 改进建议（按性价比排序）

1. **CJK 检索增强**：messages_fts/sessions_fts 迁移到 trigram tokenizer（FTS5 自带），或写入/查询两侧对 CJK 做 bigram 预处理；短期最小改动是在查询侧把 CJK 查询词同时展开为逐字 OR 补充匹配。预期直接消灭短板 1。
2. **启用向量召回补位**：真实库 embedding 100% skipped，RRF 的向量路从未生效；embedding 补上后对连写失配、同义改写都有缓解。
3. **召回融合加时间维度**：RRF 后按 `last_activity_at` 做轻量 re-rank（或对同键多值会话在 Explore prompt 中标注时间顺序），针对短板 2。
4. **给召回结果加可判别的置信信号**：返回每条命中的「查询 token 命中率」（命中了几个查询 token、是否含稀有 token），调用方即可区分强命中与「只中了『的』」；Explore/MCP 层据此拒答。针对短板 3。
5. **digest 管线**：①结构化字段程序兜底（文件路径/数值规则抽取直填 key_files，不依赖 LLM）；②窗口改为「首条用户消息 + 尾部预算」双段，超大消息截断而非整吞；③退化 digest 打标（embedding_status 式标记）并支持重试；④stale digest 定期重跑。针对短板 4/5/6。
6. **bench 自身**：时序对与拒答探针扩量（n=4/5 太小）；加同键跨会话干扰梯度（RULER hard mode）；Bench B（端到端 MCP 回答）与 LLM-as-judge 版 Bench C 作为后续。

## 本基线的局限

- 合成语料噪声为模板化生成，比真实库干净；单针 n=12、时序 n=4、拒答 n=5，百分比颗粒粗，趋势可信、个位数抖动不可信。
- Bench C 抽取器是规则式：决策句精确率抽样目测约 80%（markdown 列表/表格行有误判），"文件"含少量 `Next.js` 类框架名误判；覆盖率应读作趋势性下界。窗口复刻基于当前消息，2 个滞后 digest 的窗口与其生成时刻略有偏差。
- 拒答「误导率」按 snippet 是否含属性词判定，staging 案的 snippet 实际含否定语义（「没有 staging 环境」），该案判为误导偏严。
- 评测点是 capture-core 的 `recallSessions` 与 digest 字段，未覆盖 vesti-mcp 三工具的上层组装与 LLM 阅读 snippet 后的最终回答质量（那是 Bench B 的范围）。
